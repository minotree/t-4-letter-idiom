## 지원 크기·품질·SDK 인자

Flare / Sunburst의 공식 품질: `low`, `medium`, `high`, `xhigh`, `max`, `auto`.
권장 크기: `1024x1024`, `1024x1536`, `1536x1024`.
커스텀 크기는 다음 조건을 만족해야 합니다.

- 가로·세로 모두 16의 배수, 각 변 최대 3840px.
- 비율 1:3~3:1.
- 총 픽셀 655,360~8,294,400.
- 문서상 2560×1440을 넘는 해상도는 experimental로 표시되어 있습니다.

따라서 새 모델은 **512×1536 자체도 공식 크기 제약에 부합**합니다 (786,432픽셀, 1:3).
하지만 글자 영역까지 고려한 만화 구조를 보장하는 것은 아니므로 이번 기본 요청은 익숙한 1024×1536을 유지했습니다.
1024×3072처럼 전체 캔버스와 비율이 같은 크기로 바꾸더라도, 대사 영역과 컷 배치를 따로 설계해야 합니다.

프로젝트는 API의 모든 모델을 자동 허용하지 않습니다. `model_specs.py`의 검토된 목록만 허용합니다.
2.5 계열은 위 6개 품질, GPT Image 2는 `low/medium/high/auto`만 허용합니다.
deprecated 모델은 공식 API 종료 전이라도 프로젝트 정책으로 거부합니다.
정확한 출력 크기 검증을 위해 API가 지원하는 `size=auto`도 프로젝트에서는 거부합니다.
합성 호환성을 위해 각 변 최소 512px 조건도 추가했습니다. 이는 API 자체 조건과 구분됩니다.

설정 로딩 시와 SDK 전송 직전에 모두 검증합니다. 잘못된 모델·품질·크기는 게이트웨이 호출 전에 중단합니다.

```python
# 호출 형식만 보여 주는 예시. 이번 단계에서는 실행하지 않음.
client.images.generate(
    model="gpt-image-2.5-flare-2026-09-08",
    prompt=prompt,
    quality="medium",
    size="1024x1536",
    n=1,
    output_format="png",
)
```

`response_format`, `style`, `input_fidelity`, 스트리밍 관련 인자는 전달하지 않습니다.
기존 공식 SDK 2.54.0의 함수 서명에 인자를 바인딩하고 가짜 클라이언트로 전달값을 검사했습니다.
실제 endpoint 호환성은 미확인입니다. SDK의 품질 타입 힌트가 최신 문서보다 좁더라도 런타임 요청에서는 문자열이 전달되며,
프로젝트의 모델별 검증이 지원 품질을 확인합니다.
근거: [공식 Images SDK 레퍼런스](https://developers.openai.com/api/reference/python/resources/images/methods/generate).

## 한 장 생성과 개별 컷 생성 비교

| 항목 | 한 장에 세로 4컷 | 각 컷 개별 생성 후 합성 |
| --- | --- | --- |
| 숙어당 대본 요청 | 1 | 1 |
| 숙어당 이미지 요청 | 1 (`n=1`) | 4 (컷별 서로 다른 프롬프트, 각각 `n=1`) |
| 숙어당 전체 요청 | 2 | 5 |
| 3개 대본/이미지/전체 | 3 / 3 / 6 | 3 / 12 / 15 |
| 695개 대본/이미지/전체 | 695 / 695 / 1390 | 695 / 2780 / 3475 |
| 등장인물 일관성 | 같은 요청 안에서 유지하기 상대적으로 유리하다는 설계 판단 | 공통 캐릭터 설명이 필요하며 외모가 달라질 위험. 참조 이미지 편집 방식이면 추가 입력 이미지 비용 발생 |
| 컷 경계 | 실제 컷 높이가 불균등할 수 있어 사람의 경계 검수가 필요 | 원본 한 장이 한 컷이므로 경계 추출 불필요 |
| 실패 대응 | 한 컷이 나빠도 한 장 전체를 다시 요청할 수 있음 | 문제가 있는 컷만 다시 요청 가능 |
| 비용 | 보통 요청 수가 적으나 실비는 토큰 사용량에 따름 | 요청 수가 4배이지만 해상도별 출력 토큰이 달라 실비가 반드시 4배는 아님 |

이번 엔진의 권장 기본값은 **한 장 생성 + 사람이 확인한 경계 + 비율 유지 합성**입니다.
등장인물 일관성과 요청 수를 우선하고, 경계 위험은 자동 가정 대신 명시적인 검수 단계로 처리합니다.
향후 경계 검수를 없애고 자동 합성을 우선한다면 개별 컷 방식이 더 적합합니다.
예를 들어 개별 컷은 공식 제약에 맞는 1536×640 원본을 생성해 508×202 영역 안에 넣는 설계를 사용할 수 있습니다.
개별 컷 API·캐릭터 참조·부분 재시도 파이프라인은 이번 단계에서 구현하지 않았습니다.

## 잘림·늘어남 방지 구현

1024×1536 전체를 512×1536으로 직접 늘이거나 누르지 않습니다.
각 확인된 원본 컷을 `ImageOps.contain`으로 508×202 그림 영역 안에 비율 유지 축소합니다.
예를 들어 1024×384 컷은 약 508×190~191로 줄고, 남는 공간은 여백으로 둡니다.
대사·정답·고지는 그림과 별도 영역에 합성하며, 최종 캔버스는 512×1536입니다.

이전의 고정 4등분은 실제 만화 경계를 보장하지 못했습니다.
이제 **실제 작업에서는 경계 검수 파일이 없으면 최종 합성을 중단**하고
`status=needs_review`, `review_status=layout_pending`으로 저장합니다.
그림 체크포인트는 보관하므로 경계 확인만으로 재개할 때 그림을 다시 요청하지 않습니다.
Mock만 이전처럼 등분하며 기존 Mock 구현과 dry-run을 유지합니다.

향후 실제 그림의 `work/0001/panel_bounds.json` 예시:

```json
{
  "verified": true,
  "artwork_sha256": "해당 artwork.png 바이트의 SHA-256",
  "cut_lines": [0, 384, 768, 1152, 1536]
}
```

이 숫자는 형식 예시이며 실제 경계를 뜻하지 않습니다. 사람은 실제 그림을 확인하고 숫자를 정해야 합니다.
5개 절단 위치는 0부터 원본 높이까지 엄격히 증가해야 합니다. 전폭을 연속적으로 분할해 원본 픽셀 영역을 빠뜨리거나 중복하지 않습니다.
실제 PNG 해시와 일치해야 하며 `verified=true`가 필요합니다.
인물이 절단선을 넘지 않는다는 의미 검수 자체는 자동화하지 못하므로 사람이 잘못 확인할 위험까지 제거하지는 못합니다.
2×2 배치처럼 수평 경계로 나눌 수 없는 그림은 승인하면 안 됩니다.

`--resume-layout`은 경계 검수 대기 항목만 추가 선택하며, 일반 `needs_review`나 `completed`는 건드리지 않습니다.
재개 시 대본·그림 체크포인트를 재사용합니다. `result.json`에 실제 분할 영역과 경계 확인 여부를 기록합니다.
기존 결과와 충돌하지 않도록 파이프라인 버전을 2로 구분했습니다.
옛 Mock 체크포인트를 현재 설정으로 덮어쓰지 않으며, 향후 Mock 검증은 새 `--sandbox` 경로를 사용해야 합니다.

## 현재 가격 기준 비용 재계산

공식 Flare 일반 동기 처리 단가:

- 텍스트 입력: $5 / 100만 토큰.
- 이미지 입력: $8 / 100만 토큰 (현재 참조 없는 신규 생성에서는 0).
- 이미지 출력: $30 / 100만 토큰.
- 직접 Images API 요청에는 캐시 할인 가정을 적용하지 않음.

근거: [Flare 가격](https://developers.openai.com/api/docs/models/gpt-image-2.5-flare),
[현재 가격표](https://developers.openai.com/api/docs/pricing),
[이미지 비용 구성](https://developers.openai.com/api/docs/guides/image-generation#calculating-costs).

**medium 한 장의 출력 토큰 수와 고정 장당 실비는 미확인입니다.**
이전 GPT Image 1/1.5의 $0.063/$0.050이나 GPT Image 2의 $0.041 표를 Flare에 재사용하지 않습니다.
공식 문서도 같은 단가가 같은 장당 비용을 뜻하지 않으며 모델별 출력 토큰이 다를 수 있다고 설명합니다.

공식 단가에 적용할 수식은 다음과 같습니다.

```text
이미지 1회 = 5 × 텍스트 입력 토큰 / 1,000,000
           + 30 × 이미지 출력 토큰 / 1,000,000
대본 1회 = 0.40 × 입력 토큰 / 1,000,000 + 1.60 × 출력 토큰 / 1,000,000
```

다음은 **추정 예시**입니다. 대본 입력·출력 각각 1,000토큰, 이미지 요청마다 텍스트 입력 1,000토큰과
이미지 출력 2,000토큰을 가정합니다. 2,000은 medium의 확인된 출력량이 아닙니다.
세금·계약 할인·환전·추가 참조 이미지·실패 재요청 비용을 제외합니다.

| 방식 | 제작 수 | 대본 비용 | 이미지 API 비용 | 합계 (추정) |
| --- | ---: | ---: | ---: | ---: |
| 한 장 4컷 | 3 | $0.006 | $0.195 | **$0.201** |
| 한 장 4컷 | 695 | $1.390 | $45.175 | **$46.565** |
| 개별 4컷 | 3 | $0.006 | $0.780 | **$0.786** |
| 개별 4컷 | 695 | $1.390 | $180.700 | **$182.090** |

개별 방식도 설명을 위해 요청당 같은 토큰 수를 가정했으며, 해상도를 바꾸면 실제 차이는 달라집니다.
이미지 출력량을 요청당 1,000~4,000토큰으로 가정한 민감도 예시에서 한 장 방식의 총비용은
3개 $0.111~$0.381, 695개 $25.715~$88.265입니다. 이 범위 역시 공식 최소·최대 가격이나 보장 범위가 아닙니다.

두 작업이 모두 최대 3회 시도되고 모든 시도가 동일하게 청구된다는 보수적 예시에서는 한 장 방식의 총비용이
3개 $0.603, 695개 $139.695가 됩니다. 전체를 한 번 더 새로 제작하면 기준 추정의 2배입니다.
저장된 그림으로 경계 합성만 재개하면 추가 API 비용은 0입니다.
`--max-cost-usd`는 여전히 미구현이며 `--max-api-calls`만으로 실제 금액 상한을 보장하지 않습니다.
